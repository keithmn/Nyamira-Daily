# Decisions log

Why the site is built the way it is. Add new decisions at the bottom with a date. If you want to reverse one, discuss it first.

| # | Decision | Why |
|---|---|---|
| 1 | **Static site with Astro 5**, plain HTML output | Fast on cheap phones and slow networks, free to host (Netlify, Cloudflare Pages, GitHub Pages), nothing to hack or keep running. Astro 5 because the build environment's Node version did not support Astro 7. |
| 2 | **System fonts, no web fonts, minimal JavaScript** (fonts superseded by #19) | Pages are around 10–30 KB. Data costs matter to readers. |
| 3 | **Two-layer pages**: one number, one sentence, one label first; detail behind "See the detail" | Most readers stop after the first screen. They should still leave with something true. |
| 4 | **Evidence labels** on every figure (Verified, Audit finding, Official claim, Unverified) | Trust. See `EDITORIAL_RULES.md`. |
| 5 | **Informational, not news-heavy** | The site is a reference people return to, not a feed. Short factual updates only. |
| 6 | **Maps as inline SVG generated at build time**, no map library, no Google Maps API | Free, no API keys or usage limits, works without JavaScript, very light. Google Places was used only to discover names, never stored as coordinates (licence terms). Interactive maps (MapLibre/Leaflet + OpenStreetMap) can come later if needed. |
| 7 | **Ward pages and a site-wide ward filter, both** | The filter ("Your ward" picker, saved in localStorage) makes the whole site about the reader's ward. Ward pages remain because they can be shared on WhatsApp, found on Google, and work without JavaScript. |
| 8 | **Ward receipt** at the top of each ward page, with a WhatsApp share button | Most readers arrive from WhatsApp links; a short, forwardable summary is the main entry point. |
| 9 | **No "Coming soon" boxes.** Unfinished pages are tagged "Planned" in menus and left off the home page | Empty boxes make a site look abandoned. The list of planned pages is in `src/config.js`. |
| 10 | **Tables become stacked cards on phones** (`table.cards`) | No sideways scrolling on small screens. |
| 11 | **Share and Print at the bottom of pages**, not the top | Content first. |
| 12 | **"Tell us" and "Get updates" hidden until a contact channel exists** | Set `contact.whatsapp` or `contact.email` in `src/config.js` to turn them on. |
| 13 | **Language policy:** English written backbone; short Kiswahili summary on key pages; full Kiswahili and Ekegusii later; audio in the speaker's language with subtitles | Reach without tripling the editing load at the start. Kiswahili summaries need review by a native speaker before launch. |
| 14 | **Questions, not accusations** for projects with repeat budgeting or stalled works | See `EDITORIAL_RULES.md` section 3. |
| 15 | **Charts drawn at build time** (`src/components/BarChart.astro`) with one axis, native tooltips and the same numbers in a table | Accessible, light, no chart library. Series colours are tokens in `global.css` (light and dark). |
| 16 | **No regex literals in `.astro` frontmatter of pages that use `getStaticPaths`** | Astro's compiler mis-parsed one and failed with `Unexpected "export"`. Use helpers in `src/lib/fmt.js` instead. |
| 17 | **Dark mode supported**: follows the phone's setting, with a light/dark toggle in the header (24 Oct 2026). A small script in `Base.astro`'s `<head>` sets `data-theme` before the page draws; dark tokens are under `:root[data-theme="dark"]` in `global.css`. The reader's choice is saved in their browser; choosing the same as the phone clears it. Without JavaScript, pages are light. | Many phones default to dark mode, and some readers want to choose. The toggle takes header space, so phones narrower than about 430px show the logo symbol rather than the full logo. |

Brand colours are `--nd-*` tokens; Signal Green for fills, marks and underlines only; Record Red only for NY Watch. Default share image `public/brand/og-default.png`. | Brand guidelines. Signal Green text on white is 2.0:1, too light to read, so text is always Ink (or White on dark). |

Sizes: body 16px, h1 up to 32px, h2 up to 22px, h3 17px, big figures 27px; small labels never below 13px. | The original brand typeface decision prioritized a small download. |

| 27 | **Phase 3 datasets** (24 Oct 2026). Researched from primary sources; where a source could not be reached or was not official, the figure is left out and the gap stated (2022 full results, milk prices, KHIS). Tea figures are kept only from KTDA, the Tea Board, KNA and reputable outlets, labelled "Unverified" when only reported in the press. Comparisons show each indicator on its own with caveats, never an overall ranking. Spending per person uses the 2019 population and says so. No turnout or averages are calculated where the source gives none. Large source PDFs are listed with checksums instead of stored. | "Never invent data" over completeness: every number traces to a page, and every gap is visible to readers. |
| 28 | **Phase 4 tools** (24 Oct 2026). "What could it build?" uses only like-for-like items from the county's own records, shows the cheapest-to-dearest range, and never adjusts for inflation. | 33 | **Project progress summaries use reviewed IDs and dated physical-progress observations** (25 Oct 2026). Count each `projectId` once, selecting its latest valid observation date. Accept an explicit `observedOn` date or an explicit “as at” date in the legacy period field; never treat a financial year or source publication date as an observation date. Parse only physically labelled progress/completion/implementation percentages or supported completion wording; reject financial, target, procurement and mobilisation values, invalid values and conflicting values. Exclude and disclose projects with undated percentages, same-date conflicts, unsupported progress text or missing IDs. Do not treat expenditure percentages as physical progress, or physical completion as proof a service operates. | Row order and display names do not establish project identity or chronology. Unknown evidence stays visible instead of becoming a guessed result. |
| 34 | **Project IDs persist; aliases require reviewed evidence** (25 Oct 2026). The ID-generation script preserves existing `projectId` values instead of regenerating them from the current name. New rows with an existing normalized ward/name key reuse that ID; a different key requires an explicit alias entry naming the existing ID plus a reason and source. Keep similar work packages at the same facility distinct unless evidence confirms they are the same project. Never silently migrate existing IDs or public URLs. | Names can change and multiple projects can share a facility. Stable IDs preserve links; evidence-backed aliases avoid guessed identity merges. |
| 35 | **Project amount states stay distinct** (25 Oct 2026). Numeric zero means the source reported KSh 0; `null`/missing means no amount is available. Project CSV v2 includes `amount_status` (`reported_zero`, `reported_amount`, `unavailable`); v1 remains unchanged. | A missing value must not lower a ward's total or look like a reported zero. |
| 36 | **Financial comparisons require like-for-like measures** (25 Oct 2026). Label approved/revised budgets separately from actual expenditure. | 37 | **Opportunity availability is calculated consistently in Nairobi time** (25 Oct 2026). A stated EAT deadline is the closing instant; a date with no time closes at 23:59:59 EAT. | 43 | **Public builds fail closed on missing or placeholder domains** (25 Oct 2026). | 54 | **Facility reports: one capability per report; editors write the public record** (29 Oct 2026).
